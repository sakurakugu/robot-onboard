# 2D 激光雷达与导航重构蓝图

> 适用范围：
> - `repos/robot-onboard`
> - 2D 激光雷达：N10P（USB 串口版、网口版均已购入）
> - 目标能力：建图、定位、定点巡逻、导航任务管理

## 一、先给结论

当前 `robot-onboard` 可以继续做遥控、动作执行、音视频和云端连接，但还不适合作为“导航本体”直接接 2D 激光雷达后继续堆功能。

如果后续目标是：

- 2D 激光雷达建图
- 本地定位
- 定点导航
- 巡逻任务
- 云端查看导航状态

那么建议现在就按“导航重构”方式动，而不是先把雷达随便接上再补架构。

核心判断如下：

1. 现在的本体侧仍以“动作代理”思路为主，不是“状态感知 + 任务执行 + 导航宿主”思路。
2. 现在的状态来源分裂，协议也过于弱类型，不利于后续接入雷达、定位、地图、任务。
3. 建图和巡逻不应该继续走“动作名 + 持续时间 + sleep”的开环模型。
4. 雷达原始数据、ROS2 导航链路、云端业务协议应该分层，不能混在一个 WebSocket 消息模型里。

## 二、当前架构的主要问题

### 2.1 `robot-agent` 职责过重

当前 `robot-agent` 同时负责：

- 云端 WebSocket 通信
- 本地直连控制
- 音频采集与播放
- 视频推流
- 动作执行调度
- SDK 模式切换
- IPC 状态上报

这会导致后续再加入：

- 雷达驱动管理
- 地图保存/加载
- 定位状态
- 导航任务
- 巡逻编排

之后，`application.py` 会继续膨胀，不利于维护。

### 2.2 状态模型没有统一事实来源

当前至少存在两套状态通路：

1. `robot-agent` 子进程通过 IPC 上报状态
2. `robot-server` 通过官方 UDP 心跳拿遥测

但它们没有统一成一个标准状态对象。

现状问题：

- IPC 侧当前只上报 `battery` 和 `mode`
- `robot-server` 遥测当前只缓存 `dog_state`
- 官方已有 `imu_info`、`odom_info`、`feedback`、`navigation_state`
- 云端 `status` 还是弱类型大字典

这意味着：

- 后面加入激光雷达后，很容易再长出第三套状态链路
- UI、云端、本地服务看到的“机器人状态”可能互相不一致

### 2.3 动作系统是开环控制，不适合导航

当前动作层的主要思路是：

- `move(vx, vy, yaw_rate, duration)`
- `move_by_distance`
- `turn_around`
- 本地 `sleep`
- 被打断时发送停止命令

这套模型适合：

- 遥控
- 简单动作
- 视觉靠近

但不适合：

- 建图时稳定运动
- 定位闭环
- 路径跟踪
- 导航恢复
- 巡逻任务状态机

导航应该是“目标点 / 路径 / 取消 / 恢复 / 到达 / 失败原因”的模型，而不是“发一个动作然后等它结束”。

### 2.4 配置结构没有为导航预留空间

当前配置只有这些分组：

- `robot`
- `server`
- `media`
- `sdk`
- `audio`
- `actions`
- `logging`
- `auth`

缺少导航相关配置分组，例如：

- `lidar`
- `frames`
- `localization`
- `mapping`
- `navigation`
- `patrol`

### 2.5 云端协议还停留在“设备控制”阶段

当前云端与本体的业务消息，重点还是：

- 文本输入
- 音频输入输出
- 动作指令
- 控制指令
- 拍照
- SDK 模式

后面如果直接往现有 `status` 里硬塞地图和导航信息，会越来越乱。

## 三、重构目标

本次大重构建议把本体侧目标明确为四件事：

1. 统一本体硬件与状态模型
2. 让导航链路本地闭环运行
3. 让云端只消费“摘要状态”和“任务状态”
4. 保持音视频、语音、云控能力继续可用

最终希望形成以下能力边界：

- 本地负责：雷达、定位、建图、导航、巡逻、状态聚合
- 云端负责：任务下发、地图查看、状态展示、日志与运维
- 手机直连负责：局域网调试、手动控制、快速诊断

## 四、推荐目标架构

## 4.1 推荐拆分为四层

### A. `robot-runtime`：新增，本体运行时内核

建议新增一个新的本体子项目，例如：

- `repos/robot-onboard/robot-runtime/`

职责：

- 聚合所有本体状态
- 提供统一控制仲裁
- 管理导航任务生命周期
- 管理雷达、定位、建图、导航进程
- 对外暴露本地命令接口和状态接口

不要再让 `robot-agent` 直接操心底层导航细节。

### B. `robot-ros`：新增，ROS2 工作空间

建议新增一个 ROS2 工作空间，例如：

- `repos/robot-onboard/robot-ros/`

职责：

- N10P 雷达驱动
- `/scan`、`/tf`、`/odom`、`/imu` 发布
- 建图
- 定位
- 路径规划与导航

这里面尽量复用成熟组件，不要自己重写整套导航链路。

### C. `robot-agent`：保留，但职责收缩

保留 `robot-agent`，但改成：

- 云端桥接
- 音频/视频
- 对话
- 云端命令转发
- 状态摘要上报

不再直接承载全部本体逻辑。

### D. `robot-server`：保留，本地配置与诊断服务

保留 `robot-server`，继续负责：

- 配置编辑
- 本地诊断页面
- 日志导出
- 本地状态接口
- 运维接口

但状态数据应来自统一的 `robot-runtime`，而不是各自单独采集一份。

## 五、推荐的通信边界

## 5.1 云端 <-> `robot-agent`

继续使用现有 WebSocket 通道。

但消息职责建议变为：

- 云端发业务命令给 `robot-agent`
- `robot-agent` 转发给 `robot-runtime`
- `robot-agent` 只上报摘要状态和任务状态

不要让云端直接承载原始雷达数据。

## 5.2 `robot-agent` <-> `robot-runtime`

建议新增本地 IPC/RPC 边界，优先建议：

- Unix Domain Socket
- JSON-RPC 或简化命令协议

原因：

- 当前仓库已经有 Unix Socket IPC 经验
- 本机通信简单稳定
- 比本地 HTTP 更适合事件通知

建议支持两类通道：

1. 命令 RPC
2. 状态事件流

## 5.3 `robot-runtime` <-> `robot-ros`

建议通过 ROS2 Topic / Service / Action 通信。

职责建议如下：

- ROS2 提供：
  - `/scan`
  - `/tf`
  - `/odom`
  - `/imu`
  - 建图服务
  - 定位服务
  - 导航 Action
- `robot-runtime` 提供：
  - 启停 ROS2 子系统
  - 地图管理
  - 巡逻任务编排
  - 任务状态汇总

## 七、云端协议重构建议

建议保留现有基础消息：

- `robot_register`
- `heartbeat`
- `status`

但新增导航相关专用消息，不要全部塞进 `status`：

### 7.1 本体 -> 云端

- `robot_summary`
  - 低频摘要状态
- `navigation_state`
  - 当前导航状态
- `map_state`
  - 地图加载/建图状态
- `task_state`
  - 巡逻任务、建图任务状态
- `sensor_state`
  - 雷达、相机、音频设备状态

### 7.2 云端 -> 本体

- `navigation_command`
  - 单点导航、取消导航、恢复导航
- `map_command`
  - 开始建图、停止建图、保存地图、加载地图
- `patrol_command`
  - 启动巡逻、暂停巡逻、继续巡逻、终止巡逻

### 7.3 不建议上传的数据

以下内容不建议直接走云端业务 WebSocket：

- 原始激光扫描
- 高频 IMU 原始数据
- 高频 odom 原始数据
- 原始 TF

这些数据应本地闭环使用，仅在诊断场景下按需导出或录包。

## 九、USB 串口版和网口版怎么选

你两种都买了，建议这样用：

## 9.1 正式方案：优先网口版

正式挂载到机器狗上时，建议优先使用网口版 N10P。

原因：

- 更适合长期稳定运行
- 不占用 USB 串口资源
- 便于和音频、摄像头等 USB 设备解耦
- 你当前机器狗自带 `eth0`，后续可以专门给雷达留一条链路
- 厂商 ROS2 驱动已经支持网口参数

### 9.2 调试和备份：保留 USB 串口版

USB 串口版建议保留为：

- 台架调试
- 机械安装前快速验收
- 网口版异常时的备份链路
- 低门槛快速抓原始数据

### 9.3 建议的使用策略

推荐策略不是“二选一”，而是：

1. 先用 USB 串口版快速验收扫描数据、遮挡角、安装朝向
2. 最终正式部署切到网口版
3. USB 串口版留作备份与排障工具

## 十、Python 还是 C++

## 10.1 我的建议

不要简单地只选一种语言全做完。

建议拆分为：

- 雷达驱动和 ROS2 导航链路：优先复用现成 C++ 组件
- 业务编排、云端桥接、本地管理：继续用 Python
- 机器狗 SDK 桥接：先 Python，后续必要时再转 C++

## 10.2 激光雷达驱动：优先用现成 ROS2 驱动，不自己重写

N10P 厂商已经提供 ROS2 驱动和参数模板。

所以这里最优解不是：

- 自己写 Python 原始串口解析长期使用
- 也不是自己从零写 C++ 雷达驱动

而是：

- 直接用厂商 ROS2 驱动
- 只做参数、启动、封装和监控

Python 原始例程只适合：

- 验证串口/网口通不通
- 看原始包格式
- 排障

不适合做正式导航数据链路。

## 10.3 机器狗 SDK：先 Python 更合适

智元 SDK 同时支持 Python 和 C++，但就你当前仓库而言，建议第一阶段继续用 Python 做桥接层。

原因：

1. 现有 `robot-agent` / `robot-server` / `sparkrobot-common` 都是 Python
2. 当前团队上下文、配置体系、日志体系都在 Python
3. 你现在主要缺的是架构边界，不是语言性能
4. 用 Python 更快打通“状态聚合 + 导航命令桥接 + 云端协议”

建议第一阶段先做：

- Python `robot-runtime`
- Python 机器狗 SDK 包装
- Python 状态聚合
- Python 本地任务管理

## 10.4 哪些部分以后可以转 C++

只有在下面情况出现时，再考虑把“机器狗桥接层”改成 C++：

- 需要更高频的稳定控制循环
- Python 桥接层抖动明显
- ROS2 侧需要更紧密、低延迟的 `cmd_vel -> SDK` 转换
- 需要统一到纯 ROS2 节点体系

也就是说：

- 第一阶段：Python 更合适
- 第二阶段：如果控制实时性不够，再把狗桥接层迁到 C++

## 十一、推荐分阶段实施顺序

## Phase 0：先做架构重构，不接雷达

目标：

- 把职责边界划清
- 统一状态模型
- 把协议和配置预留好

建议输出：

- `robot-runtime` 项目骨架
- 统一 `RobotState`
- 新的配置分组
- 新的本地 IPC/RPC 协议
- 新的云端消息草案

## Phase 1：雷达单独跑通

目标：

- 先证明 `/scan` 稳定
- 确认雷达朝向、坐标系、遮挡角、数据完整性

建议输出：

- `robot-ros` 工作空间
- N10P 串口版、网口版启动配置
- `laser -> base_link` 外参
- 基础录包工具

## Phase 2：狗状态桥接到 ROS2

目标：

- 把机器狗的姿态、里程、速度统一发布到 ROS2

建议输出：

- `sparkrobot_dog_bridge`
- 发布：
  - `/imu`
  - `/odom`
  - `/tf`
- 订阅：
  - `/cmd_vel`

注意：

- 这里先不追求完美导航，先把接口桥搭起来

## Phase 3：建图与定位

目标：

- 本地完成建图、保存地图、加载地图、重定位

建议输出：

- 建图流程命令
- 地图存储规范
- 定位状态输出

## Phase 4：定点导航

目标：

- 单点导航闭环跑通

建议输出：

- `navigation_command`
- `navigation_state`
- 到达、取消、失败状态

## Phase 5：巡逻任务

目标：

- 管理多点路径和巡逻状态机

建议输出：

- waypoint 文件格式
- 巡逻任务格式
- 暂停/继续/终止
- 断点恢复策略

## 十二、立刻建议做的事

如果你现在就开工，我建议先做下面这些，不要先接雷达驱动代码：

1. 新建 `robot-runtime` 子项目骨架
2. 把本体状态统一成 `RobotState`
3. 给 `sparkrobot-common` 增加导航相关配置分组
4. 给云端协议增加 `navigation_state / map_state / task_state`
5. 把 `robot-agent` 从“底层控制宿主”收缩成“云端桥接器”
6. 设计 `robot-runtime <-> robot-agent` 的本地 IPC/RPC
7. 新建 `robot-ros` 工作空间
8. 再接 N10P 网口版作为正式导航链路

## 十三、我对语言和硬件的最终建议

一句话版本：

- 正式部署：优先网口版 N10P
- USB 串口版：保留给调试和备份
- 雷达驱动：直接用厂商 ROS2 驱动
- 业务层和本体编排：继续 Python
- 机器狗 SDK 桥接：先 Python，必要时再转 C++

这是当前对你这个仓库最稳、返工最少的方案。
